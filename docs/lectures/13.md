# 13 Raft 基础、日志与选举

源码：`src/raft/mod.rs`、`src/raft/log.rs`、`src/raft/state.rs`、`src/raft/message.rs`、`src/raft/node.rs`。  
文档：`docs/architecture/raft.md`。  
测试：`src/raft/testscripts/log/`、`src/raft/testscripts/node/` 的 election/tick 系列。

## 13.1 Raft 提供什么、不提供什么

Raft 让一组节点对 **命令日志** 达成一致，再按相同顺序应用到确定性状态机。性质：

- 多数派活着才能提交。
- 已提交写线性一致可见（读还要额外确认领导权）。
- 多数派持久化后，写不丢。

Raft **不** 提供：SQL 事务隔离（那是 MVCC）、水平扩展（每节点全量数据、Leader 处理所有请求）、分片。

状态机必须确定性：不能在 apply 里读时钟或随机数。非确定性错误必须 panic，否则节点会分叉。

模块注释里的 SQL 字符串日志只是示意。真实命令是 Bincode 的 `Write` 枚举，见第 15 章。

## 13.2 日志与状态机接口

`Entry { index, term, command: Option<Vec<u8>> }`。index 从 1 连续。`command=None` 是选主后的 noop，用来提交旧任期条目（论文 5.4.2）。

日志存在 `storage::Engine` 里：

```text
Key::Entry(index) → Entry
Key::TermVote     → (term, vote)
Key::CommitIndex  → (index, term)
```

不变量（`log.rs` 注释）：无缺口；term 不降；已提交条目不变；相同 index/term 意味着相同命令；若两日志在某 index/term 相同，则之前全部相同。

`raft::State`：`get_applied_index`、`apply(entry)`、`read(command)`。状态机可以落后，崩溃后从 applied+1 重放。`read` 禁止写。

`Log::new` 从磁盘恢复 term/vote、最后一条、commit index。`set_term_vote` **总是 fsync**，即使 `Log::fsync=false`，因为双投票会导致双主。

## 13.3 角色、tick、step

`Node` 是 Candidate / Follower / Leader 三变体，内部 `RawNode<Role>` 是 typestate：只有 Candidate 有 `into_leader()`。

驱动完全同步：

- `tick()`：逻辑时钟。默认 100ms 一 tick。选举超时 10–20 ticks，心跳每 4 ticks。
- `step(Envelope)`：处理一条入站消息。消耗 self，返回可能换了角色的 Node。
- 出站消息走 `tx: Sender<Envelope>`。

消息可以丢、可以乱序（协议按此设计）。toyDB 用 TCP，连接不断时实际更可靠。单节点集群创建时直接变成 Leader。

## 13.4 选举过程

节点以无 Leader 的 Follower 起步。收不到心跳直到随机超时 → Candidate：term+1，投自己，发 `Campaign { last_index, last_term }`。

Follower 若 term 更新则跟上；本任期尚未投票且候选人日志足够新则给票，并 **持久化** vote。多数票 → Leader，发 Heartbeat，并追加一条空日志。

随机超时减少平票。平票则大家再超时、再加 term。测试：`election`、`election_tie`、`election_contested`。

## 13.5 投票安全

- 每个 term 最多一票，落盘，重启仍记得。
- 候选人日志必须至少和投票者一样新：先比 last term，再比 last index（论文 5.4.1）。**不能只比长度。**
- 旧 term 消息忽略；更高 term 使本节点立刻变 Follower。

这保证新 Leader 的日志包含所有已提交条目。

## 13.6 请求转发与中止

客户端请求是 `Message::ClientRequest { id: UUID, request }`。Follower 转给 Leader，响应按 id 送回。Candidate 上的请求直接 `Error::Abort`。角色变化、发现新 Leader 时，未完成请求也 Abort。不在内部重试，避免重放语义。客户端应重试；不保证 exactly-once。
