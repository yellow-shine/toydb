# 14 Raft 复制、读取与恢复

源码：`src/raft/node.rs`、`src/raft/log.rs`、`src/raft/message.rs`。  
测试：`src/raft/testscripts/node/` 的 append、heartbeat、restart、read_quorum、linearizability 等。

## 14.1 写入何时算成功

Leader 收到 `Request::Write`：

1. `Log::append` 写入本地并按配置 fsync。
2. 向 Follower 发 `Append`。
3. 多数派（含自己）匹配该 index 后 `Log::commit`。
4. `State::apply`，结果经 `ClientResponse` 返回。

本地落盘 ≠ 成功。多数派复制 ≠ 已经 apply。客户端成功 ⇒ 已提交且 Leader 已 apply。Follower 的 apply 可以稍后靠心跳里的 `commit_index` 赶上；正确性不依赖 Follower 立刻 apply，因为读只在 Leader 上做。

提交还有当前任期限制：Leader 不能只靠复制旧任期条目来提交它们，所以当选后先追加 noop（论文 5.4.2）。

## 14.2 日志匹配与冲突

`Append` 带 `base_index/base_term`。Follower 在该位置有相同 index/term，则日志到此一致，可以追加（冲突的未提交后缀会被 `splice` 截掉再写）。否则拒绝。

`splice`：跳过已经相同的条目；从第一个 term 不同处截断本地未提交尾，写入新条目。不能改 commit_index 以下。

探测用空 Append 降低 base，直到匹配，再批量补齐。`reject_index` 可直接跳过 Follower 日志短于 base 的那些空洞。

## 14.3 每个 Follower 的进度

Leader 为每个 peer 记 `next_index` / `match_index`（`Progress`）。稳态一次发少量条目（`MAX_APPEND_ENTRIES`）。过时或重复的 AppendResponse 不能让 match_index 倒退到破坏提交。心跳里的 `last_index` 用来发现丢消息或日志分叉。

## 14.4 线性一致读

读不进日志，只在 Leader 上 `State::read`。但分区下旧 Leader 可能不知道自己已经不是 Leader。

因此每次读：Leader 增加 `ReadSequence`，发 `Message::Read`，多数派确认该序号后才执行读。这比写还多一趟网络。生产系统常用 lease；toyDB 没有。

读还要等状态机应用到足够新的 index，否则可能读到过期快照。测试：`request_leader_read_quorum`、`request_leader_change_linearizability`。

这保证的是 **单次 Raft 读操作** 的线性一致性，不是 SQL 事务可串行化。事务里仍可能看到 SI 快照。

## 14.5 重启

重启后：日志条目、term、vote 从引擎恢复。commit index 若丢了，可从多数派再学到。状态机若丢了尾巴，从 `get_applied_index()+1` 重放到 commit。因此状态机不必每条 apply 都 fsync；Raft 日志才是耐久源。

`applied_index` 与 `commit_index` 不同：前者是状态机进度，后者是日志不可变前缀。

测试：`restart`、`restart_apply`、`restart_commit_recover`、`restart_term_vote`。

## 14.6 错误与不确定结果

`Error::is_deterministic`：`InvalidInput` / `ReadOnly` / `Serialization` 为真，apply 失败也算已应用，可返回客户端。`IO` / `InvalidData` / `Abort` 为假，apply 时 panic，避免分叉。

Leader 切换会使进行中的请求 Abort。客户端重试可能二次执行——toyDB 不做请求去重。

## 14.7 明确没有的能力

无 leader lease、无在线成员变更、无快照、无日志截断（日志永久保留）、无 pre-vote/check-quorum、无内部请求重试、探测不带复杂 hint 优化。不要把论文后半的生产机制当成已实现。
