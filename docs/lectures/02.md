# 02 BitCask 持久化

源码：`src/storage/bitcask.rs`。  
测试：`src/storage/testscripts/bitcask/`，以及共用的 `src/storage/testscripts/engine/`。

## 02.1 只追加写，为什么还能覆盖更新和删除

BitCask 不原地修改旧记录。`set` 把新记录追加到文件末尾，并更新内存索引 KeyDir；`delete` 追加 tombstone，再从 KeyDir 删掉该 key。

```rust
fn set(&mut self, key: &[u8], value: Vec<u8>) -> Result<()> {
    let value_location = self.log.write_entry(key, Some(&*value))?;
    self.keydir.insert(key.to_vec(), value_location);
    Ok(())
}

fn delete(&mut self, key: &[u8]) -> Result<()> {
    self.log.write_entry(key, None)?;
    self.keydir.remove(key);
    Ok(())
}
```

逻辑数据以 KeyDir 为准：它永远指向该 key **最后一次** 成功写入的位置。文件里可以同时存在 `b=1` 和后来的 `b=2`；`get("b")` 只读后者。

删除后 `get` 返回 `None`，即使文件里还有旧值和 tombstone。这就是“追加写文件实现可更新 KV”的核心。

## 02.2 磁盘记录布局

一条记录：

```text
keylen:  big-endian u32   4 字节
valuelen: big-endian i32  4 字节；-1 表示 tombstone
key:     原始字节
value:   原始字节（tombstone 无 value）
```

`foo=bar` 即 `00000003 00000003 666f6f 626172`。

`write_entry` 先 `seek(End)`，用 `BufWriter` 写出，再 `flush` 到文件（此时尚未 fsync）。返回的 `ValueLocation` 指向 **value 的偏移和长度**，不含 8 字节长度前缀和 key。KeyDir 用这个位置做随机读。

toyDB 只用一个任意大小的日志文件，没有标准 BitCask 的多文件、checksum、时间戳、hint file。

## 02.3 打开文件、重建 KeyDir、不完整尾记录

打开时对文件加独占锁，扫描全文件重建 KeyDir：

- 普通记录：`keydir.insert(key, value_loc)`
- tombstone：`keydir.remove(&key)`
- 读到 `UnexpectedEof`：视为崩溃留下的半截写入，`set_len(offset)` 截掉尾部，停止扫描

同一 key 出现多次时，后出现的记录覆盖 KeyDir。这与运行时 `set` 的规则一致，所以重启后逻辑内容与崩溃前最后一次完整写入相同。

`src/storage/testscripts/bitcask/log` 先乱序写入、覆盖、删除，`scan` 只看到最终 live 数据；`dump` 则按文件顺序列出每一条物理记录，包括已被覆盖的 `b=1` 和 tombstone。`reopen` 后再 `scan`，live 数据不变。

单元测试 `recovery` 把文件截断到每一个字节偏移，断言总能恢复某个完整前缀。

## 02.4 flush、fsync 与“写入成功”

`write_entry` 的 `w.flush()` 只保证写到 OS。真正的持久化是：

```rust
fn flush(&mut self) -> Result<()> {
    #[cfg(not(test))]
    self.log.file.sync_all()?;
    Ok(())
}
```

测试构建里 `flush` 是空操作，为了跑得快。注释特意说明：不要靠关掉 Raft 的 fsync 来加速测试，而要在这里跳过，这样才能继续断言 Raft 日志“调用了 flush”。

`Drop` 会再调一次 `flush`。接口约定：**写入成功不等于已经耐久**；耐久要等 `Engine::flush()`。Raft 日志在 `append`/`splice` 后会按配置调用它。

## 02.5 有序扫描：KeyDir 有序，文件不必有序

```rust
fn scan(&mut self, range: impl RangeBounds<Vec<u8>>) -> Self::ScanIterator<'_> {
    ScanIterator { inner: self.keydir.range(range), log: &mut self.log }
}
```

KeyDir 是 `BTreeMap`，按 key 字节序迭代。每一项再用 `log.read_value` 按偏移读磁盘。因此：

- 逻辑扫描顺序由内存索引决定。
- 磁盘上的记录顺序是追加顺序，可以完全不同。
- 扫描时需要 `&mut Log`，因为读文件要 `seek`。

这与 01 的接口相同，所以上层（MVCC、SQL、Raft 日志）不必知道下面是 Memory 还是 BitCask。

## 02.6 压缩、打开策略与容量限制

`compact` 建临时 `.new` 文件，按当前 KeyDir 把所有 live 值写出，`rename` 替换原文件，换上新 KeyDir。tombstone 和旧版本不再写入。压缩期间读写都被挡住；toyDB 只在启动时考虑压缩。

`new_maybe_compact` 看 `garbage_disk_size` 是否同时达到最小字节和最小比例。`status` 里：

- `disk_size`：文件长度
- `size`：live key 字节 + live value 字节
- `live_disk_size`：`size + 8 * keys`（计入每条记录的长度前缀）

所有 live key 必须放进内存。key 很多时这是硬限制，不是可调优化。

`src/storage/testscripts/bitcask/compact` 和 `compact_open` 覆盖主动压缩与打开时压缩。
