# 04 MVCC 版本与可见性

源码：`src/storage/mvcc.rs`。  
文档：`docs/architecture/mvcc.md`，以模块注释为准。  
测试：`src/storage/testscripts/mvcc/`。

## 04.1 多版本怎么存

用户看到的还是 `get/set/delete(key)`。引擎内部把每次写变成：

```text
Key::Version(user_key, version) → Option<value>
```

`version` 是 `u64` 逻辑序号，不是墙上时钟，也不是 Raft index。删除把 value 编成 Bincode 的 `None`（tombstone），不是直接从引擎删掉历史。

同一用户 key 的多个版本因为 Keycode 保序，会挨在一起，并且按 version 递增。读最新可见版本可以对该区间做反向扫描。

另外还有不参与事务的 `Key::Unversioned`，给 Raft 存 `applied_index` 这类元数据。它和同名的 versioned key 完全独立。

## 04.2 NextVersion 与活跃集合

读写事务开始时：

1. 读 `Key::NextVersion`（没有则从 1 开始），把 `version+1` 写回去。
2. 扫描所有 `Key::TxnActive(*)`，得到当前未提交事务集合。
3. 若该集合非空，写成 `Key::TxnActiveSnapshot(version)`，给以后的时间旅行用。
4. 写入 `Key::TxnActive(version)`，把自己标成活跃。

`TransactionState` 保存 `version`、`read_only`、以及开始时的 `active: BTreeSet<Version>`。这个快照之后不再跟着别人的提交而更新。

## 04.3 可见性规则

```rust
fn is_visible(&self, version: Version) -> bool {
    if self.active.contains(&version) {
        false
    } else if self.read_only {
        version < self.version
    } else {
        version <= self.version
    }
}
```

三条：

- 开始时仍活跃的版本不可见（那些事务当时还没提交）。
- 读写事务能看见 `<= 自己 version` 的已提交版本，包括自己的未提交写。
- 只读 / 时间旅行只看见 **严格小于** 自己 version 的版本，避免“那个 version 的原事务后来提交了，历史查询却前后不一致”。

比自己新的版本自然不可见。

## 04.4 单点读

`get` 扫描 `Key::Version(key, 0) ..= Key::Version(key, self.version)`，**反向**取，跳过不可见版本，遇到第一个可见值就解码 `Option<Vec<u8>>`。`None` 表示该版本是删除。

`src/storage/testscripts/mvcc/get` 与 `get_isolation` 覆盖点查和隔离。

## 04.5 范围读如何折叠版本

`scan` 把用户 key 范围翻译成引擎 key 范围。例如包含 `k` 的起点变成 `Key::Version(k, 0)`，让该 key 的所有版本都进入窗口。

`ScanIterator` 不在整个扫描期间握着引擎 mutex。它一次缓冲 32 项（测试里是 2），中间释放锁，避免 SQL Join 同时扫两张表时死锁。

内部 `VersionIterator` 丢掉不可见版本。`ScanIterator` 再看相邻项：若下一对仍是同一用户 key，说明当前不是最新可见版本，跳过；若是最新且 value 不是 tombstone，才输出。

MVCC 的 `ScanIterator` **不是** `DoubleEndedIterator`。底层 Engine 支持反向扫描，事务层范围读目前只正向，因为 SQL 用不到反向。

`scan_isolation`、`scan_key_version_encoding`、`scan_prefix` 覆盖这些行为。

## 04.6 共享、锁、与隔离的区别

```rust
pub struct MVCC<E: Engine> {
    pub engine: Arc<Mutex<E>>,
}
```

底层 `Engine` 不是线程安全的，所以所有读写串行化。Raft 状态机也是一条命令一条命令 apply。这把 **物理执行** 变成单线程。

快照隔离来自版本和活跃集合，不是来自这把 mutex。mutex 不提供可串行化，也不阻止写冲突——写冲突是 `write_version` 里显式检测的。
