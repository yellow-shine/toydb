# 17 测试、工具与端到端串讲

源码：`tests/tests.rs`、`tests/testcluster.rs`、`tests/scripts/`、`src/bin/toydump.rs`、`src/bin/workload.rs`、`src/encoding/format.rs`、`.github/workflows/ci.yml`。

## 17.1 Goldenscript

`goldenscript` 跑脚本：命令、`---`、预期输出。`test_each_path!` 把目录里每个文件变成测试。

Engine 共用 `src/storage/testscripts/engine/`，Memory 和 BitCask 都跑；各自还有 `memory/`、`bitcask/`。Raft node 脚本描述消息时序。SQL 脚本覆盖表达式、优化、查询、写入、事务异常。

改行为而不改脚本会失败。脚本是行为文档。

## 17.3 诊断工具

`toydump` 把 BitCask/Raft/SQL 文件打成可读 key/value（`encoding::format`）。`status` 有引擎垃圾比例、MVCC 版本数、Raft 状态。日志用 simplelog。EXPLAIN 看计划。VSCode+CodeLLDB 配置在 `.vscode/launch.json`。

## 17.4 workload

`read` / `write` / `bank`。bank 带 Join、二级索引、冲突。README 表格说明 fsync 把写性能打到极低；关 fsync 或用 Memory 会快很多，但破坏 Raft 耐久假设。不要把表格数字当回归基准，机器不同会变。

没有写批处理：每条 Raft append 都可能 fsync，这是写慢的主因之一。

## 17.5 追一条 SELECT

以 `SELECT title FROM movies WHERE id = 1` 为例（主键等值，优化后应是 KeyLookup）：

1. `toysql` → TCP `Request::Execute`
2. `Session::execute` → Parser → AST Select
3. `with_txn(true)` → Raft `Read::BeginReadOnly`（多数派确认领导权后，Leader `Local.begin_read_only`）
4. `Plan::build` + `optimize`：FilterPushdown + IndexLookup → `KeyLookup`
5. `Executor` → `txn.get(movies, [1])` → Raft `Read::Get { txn state, ... }`
6. 再一次线性一致读，Leader resume 事务，MVCC get 可见版本，返回行
7. 隐式事务只读 commit 为空操作
8. 行缓冲进 `StatementResult::Select` 发回客户端

连接的节点若是 Follower，2 之后的 Raft 请求由本机节点转发 Leader。

## 17.6 追一条 INSERT 与 COMMIT

显式事务：

1. `BEGIN` → `Write::Begin` 复制，分配 MVCC version，Session 保存 state
2. `INSERT` → `Write::Insert { txn: state, rows }` 复制，各节点 `resume` 后 Local insert（校验、行、索引）
3. `COMMIT` → `Write::Commit { state }` 复制，各节点删掉 TxnActive，写对后续事务可见

三次写，三次多数派。成功回复发生在 Leader apply 对应命令之后。Follower 的 SQL 会话仍在原节点，只是命令在 Leader 上提交。

隐式单条 INSERT：Begin + Insert + Commit 三次写，Session 不保留 txn。

## 17.7 冲突与 Leader 故障

两事务写同一行：后 apply 的 `write_version` 返回 `Serialization`（确定性错误，算已应用）。客户端应 rollback/重试。`tests/scripts/anomalies`、`isolation` 在 SQL 层演示。

Leader 崩溃：进行中的 ClientRequest Abort；选举后新 Leader 带上已提交日志。客户端重试 BEGIN/INSERT 可能重复——没有请求 id 去重。本地 node 脚本展示协议；`TestCluster` 杀进程才能观察真实故障，两者证据范围不同。

## 17.8 全景

```text
字节有序 KV  →  追加日志 BitCask  →  保序编码
    →  MVCC 快照隔离
    →  SQL 表/索引映射
    →  解析 / 规划 / 优化 / 执行 / 会话
    →  把存储操作复制进 Raft
    →  TCP + 线程把客户端接到节点
```

保证分层：BitCask flush 管磁盘；Raft commit 管复制耐久与线性一致单次读写；MVCC SI 管事务切面；SQL 管约束与查询语义。

资源瓶颈（刻意不解决）：全 key 内存、无 MVCC GC、Raft 日志不截断、Leader 单点、扫描整表缓冲、每写可能 fsync。

可选修改练习只在主动要求时再做。本讲义覆盖学习地图中的全部知识点编号。
