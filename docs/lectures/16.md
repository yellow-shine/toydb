# 16 Server、Client 与进程启动

源码：`src/server.rs`、`src/client.rs`、`src/bin/toydb.rs`、`src/bin/toysql.rs`、`src/error.rs`。  
文档：`docs/architecture/server.md`、`docs/architecture/client.md`。  
运行：`cluster/run.sh`、`cluster/toydb1/toydb.yaml`。

## 16.1 进程组装

`toydb` 读 yaml + `TOYDB_` 环境变量：节点 id、peers、监听地址、data_dir、raft/sql 用 bitcask 还是 memory、fsync、压缩阈值。

然后：

- `data/raft` → BitCask/Memory → `raft::Log`，按配置 `enable_fsync`
- `data/sql` → BitCask/Memory → `sql::engine::Raft::new_state`（即 `raft::State`）
- `Server::new(...).serve(listen_raft, listen_sql)`

Raft 日志和 SQL 状态机是 **两个独立引擎文件**，不要当成同一个 BitCask。

## 16.2 线程模型

不用 async。`thread::scope` 里：

- 接受 Raft TCP
- 对每个 peer 一条出站连接线程（失败则 1s 重试）
- `raft_route`：tick 节点、step 入站消息、把出站 Envelope 发给 peer 或本地等待者
- 接受 SQL TCP

通道是 Crossbeam。Raft 节点单线程 step，保证确定性。SQL 连接各自一个 Session 线程，通过通道把 `raft::Request` 交给 route 线程。

## 16.3 两个端口

SQL 与 Raft 分开监听。示例：SQL 9601–9605，Raft 9701–9705。协议是 Bincode 消息，没有额外 length prefix 帧——解码器知道一个值读到哪里。

入站 Raft：`Envelope::maybe_decode_from`。出站：`encode_into` + flush。SQL 同理，类型是 `server::Request/Response`。

## 16.4 请求 ID 与等待

SQL 引擎 `Raft::request` 建 bounded(1) 响应通道，把 `(raft::Request, tx)` 发给 route。route 把它变成 `ClientRequest { id: UUID, ... }` step 进节点。节点发出的 `ClientResponse` 按 id 找回通道。

Follower 上的 SQL 连接同样把请求交给 **本机** Raft 节点，由 Raft 转发到 Leader，响应再回来。调用方阻塞在 `response_rx.recv()`。

## 16.5 SQL 连接生命周期

`sql_accept` 每连接建 `engine.session()`，循环读 `Request::Execute(sql)`，`Session::execute`，写回 `Response::Execute`。还有 GetTable、ListTables、Status。断连则 Drop Session，未提交事务 rollback。

`StatementResult::Select` 已含全部行。没有流式协议。

## 16.6 Client 与 toysql

`Client` 连 SQL 端口，Bincode 收发。`execute` 根据 Begin/Commit/Rollback 更新本地缓存的 `txn` 状态（展示用）。不是 MySQL/PostgreSQL 协议。

`toysql` 是 rustyline REPL，把输入交给 `Client::execute` 并打印。`!help` 等是客户端命令，不进 SQL 解析器。

错误：`Abort` 应重试；`Serialization` 应重开事务；`InvalidInput` 改 SQL。没有自动重试循环。
