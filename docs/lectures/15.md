# 15 SQL 与 Raft 的连接

源码：`src/sql/engine/raft.rs`、`src/sql/engine/local.rs`、`src/raft/state.rs`、`src/storage/mvcc.rs`。  
文档：`docs/architecture/sql-raft.md`。

## 15.1 同一 SQL 接口，两套实现

查询处理（Parser/Planner/Executor/Session）只依赖 `sql::engine::Engine`。`Local` 直接调 MVCC；`Raft` 把每次存储调用变成一条 Raft 请求。节点进程永远用 Raft 引擎；大量 SQL 单元测试用 Local+Memory。

## 15.2 复制的不是 SQL 字符串

`Write` / `Read` 枚举对应 Engine/Transaction 方法：`Begin`、`Insert { txn, table, rows }`、`Scan { txn, table, filter }` 等。Bincode 编码后放进 `raft::Request::Write/Read`。

`INSERT INTO t VALUES (1)` 会变成：可能已有的 `Write::Begin`、`Write::Insert`、`Write::Commit`。EXPLAIN 不写。SELECT 走 Read，不追加日志。

## 15.3 事务状态放在命令里

Leader 可能换人，节点可能重启，不能把 `mvcc::Transaction` 对象留在某台机器内存里。于是每条命令携带 `TransactionState`，状态机 `resume` 后再执行。

Session（在接到 SQL 的那个节点上）记住这份 state。客户端 TCP 会话不直接持有 MVCC 锁。

只读 `BeginReadOnly` 走 Read，避免为只读快照复制一条日志。读写 `Begin` 走 Write，因为要分配 version、写活跃集合。

## 15.4 apply / read

`State::apply`：

1. 断言 `entry.index == applied_index + 1`。
2. 无 command（noop）→ 空结果。
3. 有 command → `Write::decode` → `Local.resume(...).insert/commit/...`。
4. 非确定性错误 panic。
5. 把 `applied_index` 写入 unversioned key `b"applied_index"`，不强制 fsync。

`State::read` 解码 `Read`，同样 resume 后调 Local。`Read::Scan` 把迭代器 `collect` 成 `Vec<Row>` 再编码。

## 15.5 持久性从哪来

MVCC `commit` 不 flush。Raft `append` 在配置允许时 flush 日志。崩溃后重放未 apply 的已提交日志，SQL/MVCC 状态追上。

SQL `COMMIT` 本身是一条 `Write::Commit`，也要走完整复制。隐式事务的一条 INSERT 实际是 Begin + Insert + Commit 三次写。

BitCask 压缩、MVCC 历史、Raft 日志是三份不同的“旧数据”，互不清理对方。

## 15.6 读：Raft 协调 + MVCC 快照

SELECT 不写日志，但 Leader 仍要 ReadSequence 多数派确认（第 14.4 节）。确认后 `State::read` 用事务的 MVCC 快照读，不是“读物理最新版本”。另一个已提交事务若在本快照之后，仍然不可见。

所以：**线性一致** 保证这次读不会落在更晚的 Raft 写之前；**SI** 保证事务内部看到开始时的切面。两套保证叠在一起，不要说成一种。

## 15.7 扫描不是全程流式

`Local::scan` 返回迭代器。`Raft::scan` 在 Leader 上收集成 `Vec`，Bincode，再当一条 ClientResponse 发回来。全表扫描会把整表放进内存、放进网络消息。底层 Engine 的惰性迭代到这里就断了。Session 再收集一次给 TCP 客户端。这是刻意简化。
